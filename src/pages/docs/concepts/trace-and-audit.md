## 为什么需要 Trace

在复杂的智能体与提示词系统中，经常会遇到令人困惑的问题：

- “为什么模型突然忘记了某条关键设定？”
- “某条世界观规则到底有没有被激活？”
- “超长对话时，被截断丢弃的究竟是哪部分信息？”

如果系统是一个黑盒，调试将变成漫无边际的盲猜。Loom Studio 从第一天起就将**端到端可解释性（Explainability）**作为核心原则。

## 构建流水线的每一步都有记录

在每一次提示词构建（PromptBuild）过程中，Loom Core 都会生成结构化的 Trace 事实：

~~~text
Facts 收集 → 规则匹配 (Activation Trace)
  ↓
槽位映射与排序 (Ordering Trace)
  ↓
Token 预算与裁剪 (Budget Trimming Trace)
  ↓
最终发送给模型的 Payload (Compiled Output)
~~~

创作者和开发者可以在 Studio 的检查器中清晰看到：
1. **谁被激活了**：命中了哪些关键词或状态条件；
2. **谁被抑制了**：为什么某些条目未进入上下文；
3. **最终排布**：每个片段在整体 Prompt 中的确切位置和 Token 消耗。

## 变更集与状态审计（Changeset）

除了提示词构建，系统中的每一次数据写入也遵循可审计的 **Changeset（变更集）** 机制：

- 所有的剧情推进、状态变更和变量修改，都通过单事务原子提交；
- 每次提交生成不可变的版本 Revision；
- 回滚操作不会暴力覆盖历史，而是生成一个明确的反向补偿变更集。

这种严谨的架构保证了长篇互动创作过程中的数据绝对安全，也为未来的多分支世界线协作提供了坚固的地基。
